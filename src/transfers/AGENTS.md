# transfers

## Purpose

The app-side transfer workflow: every attempt is an `intents` row in the app DB, authorized against the bank, dispatched once under a stable bank reference, and reconciled with the bank when the outcome is ambiguous. Owns the `transfer_money` and `operation_status` agent tools and the `approvals/:id/confirm` endpoint. `POST /api/actions` is served by `assistant/entry-points/http/run-action.ts` (moved in 7b, layered in 7c); the URL did not change.

Hexagonal vertical (plan §10): `domain/` (pure rules), `application/` (ports, services, use cases), `infrastructure/` (adapters), `entry-points/` (wiring, tools, http, the frozen legacy surface). Nothing else lives at the root but `index.ts` and this file.

## For AI Agents

### Working In This Directory

- Layer rules are enforced by ESLint (`eslint.config.mjs`, plan §10): `domain/` is pure (no clock, random, I/O or `platform/`); `application/` never imports `platform/` or infrastructure; only `dependencies.ts` and `legacy.ts` touch infrastructure; `index.ts` re-exports `./entry-points/` only.
- Every caller (tools, http, legacy, other features) goes through the `transfers()` singleton, so the in-flight `DispatchRegistry` is shared. A second `wireTransfers()` graph has its own registry: use one only in tests.
- Money state is owned by the bank (`simulator/`), not the app DB. `intents` is only the app's record of attempts (statuses: `IntentStatus` in `domain/transitions.ts`).
- Bank contract (idempotency by actor + reference, error codes) is in `docs/contracts.md`; do not change `simulator/` to make this code pass.
- Other features import this one only through `index.ts`.
- Things worth scrutinizing:
  - `payloadOf` and `previous.payload` comparison depend on key order (schema order).
  - The role check throws a `ForbiddenError` while bank failures after the dispatch return `{status:'failed'|'unknown'}`; `runTool` converts thrown errors into tool errors by message.
  - Single instance assumed: the in-flight registry is per process. `dispatched_at` covers restarts and HMR (a dispatch that died is settled once stale), but two app instances dispatching the same intent would not see each other's registry.
  - The override matches only the newest unresolved twin, so with several pending twins each "send anyway" acknowledges the newest one.
  - `failed` intents never hold a twin: a `failed` is a bank rejection or a 404 verified after the stale window, so a new identical transfer is legitimate. Recent `failed` intents with a reference are still re-checked on the dashboard for 24 h, so a late commit shows as completed.
  - A `requires_review` from the agent leaves a `created` intent with no approval; the customer resolves it through the Transfers form ("Send anyway") or by waiting for the dashboard check.
  - Known friction: "Send anyway" on a held proposal only lifts the hold for that proposal. Confirming it while the twin is still unresolved is held again, so the customer is asked a second time; the override is not remembered between the two requests.
  - `operation_status` accepts any reference string; scoping relies on the bank enforcing the actor header.
  - Pre-flight checks are advisory and persisted with the approval: a reused live approval returns its stored checks (the card and the model agree), so a balance read at proposal time can be stale by confirmation; the card shows "as of {time}". The first-time check knows only the app's intents (movements carry no counterparty), hence the wording "through Banana Bank's app".

### Testing Requirements

- Every module has a sibling `*.test.ts`; the bank-touching ones run against the real bank over HTTP (`tests/support/bank.ts`, `startLossyBank(lose, fault?)` for lost responses and `hang` + `release()` for a dispatch held in flight); never mock `bankRequest`.
- Service tests use `wireTransfers().internals`, one graph per file; use-case tests default to the `transfers()` singleton (or one `wireTransfers()` graph when a case needs the registry). Time- or id-dependent cases live in `describe('… with a fixed clock')` and wire `wireTransfers({ clock: fixedClock(), ids: sequentialIds(…) })`.
- `entry-points/legacy.test.ts` pins the frozen `HttpError` / `BankError` classes; the `http/` handler is covered by `app/api/[...path]/route.test.ts`.

### Common Patterns

- The bank is reached only through the `TransfersBank` port; always pass the server-known `ctx.userId`.
- Intent ids are `<runId>:<tool call_id>`, giving one intent per model tool call.
