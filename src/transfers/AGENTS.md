# transfers

## Purpose

The app-side transfer workflow: every attempt is an `intents` row in the app DB, authorized against the bank, dispatched once under a stable bank reference, and reconciled with the bank when the outcome is ambiguous. Owns the `transfer_money` and `operation_status` agent tools and the `actions` and `approvals/:id/confirm` endpoints. The bank itself is reached only through the port in `../platform/bank/`.

## For AI Agents

### Working In This Directory

- Intent and approval rows are read and written only through `intents.repo.ts` and `approvals.repo.ts`. Intent status changes go through `intent-lifecycle.ts:transition`; a field-only write (`bank_reference` in `dispatch.ts`) calls the repo directly.
- Money state is owned by the bank (`simulator/`), not the app DB. `intents` in the app DB is only the app's record of attempts (statuses: `IntentStatus` in `intent-lifecycle.ts`).
- Bank contract (idempotency by actor + reference, error codes) is in `docs/contracts.md`; do not change `simulator/` to make this code pass.
- Other features import this one only through `index.ts`; inside the feature import relatively.
- Things worth scrutinizing:
  - `transfer-money.ts`: `previous.payload` comparison is on `JSON.stringify` key order.
  - `transfer-money.ts`: role check throws `HttpError` while later failures return `{status:'failed'}`; `runTool` converts both into tool errors.
  - Single instance assumed: the in-flight registry (`dispatch.ts:isDispatching`) is per process. `dispatched_at` covers restarts and HMR (a dispatch that died is settled once stale), but two app instances dispatching the same intent would not see each other's registry.
  - The override matches only the newest unresolved twin, so with several pending twins each "send anyway" acknowledges the newest one.
  - `failed` intents never hold a twin: a `failed` is a bank rejection or a 404 verified after the stale window, so a new identical transfer is legitimate. Recent `failed` intents with a reference are still re-checked on the dashboard for 24 h, so a late commit shows as completed.
  - A `requires_review` from the agent leaves a `created` intent with no approval; the customer resolves it through the Transfers form ("Send anyway") or by waiting for the dashboard check.
  - Known friction: "Send anyway" on a held proposal only lifts the hold for that proposal. Confirming it while the twin is still unresolved is held again (`requires_review` on `POST /api/approvals/:id/confirm`), so the customer is asked a second time; the override is not remembered between the two requests.
  - `operation_status` accepts any reference string; scoping relies on the bank enforcing the actor header.

### Testing Requirements

- Every module has a sibling `*.test.ts`; the bank-touching ones run against the real bank over HTTP (`tests/support/bank.ts`, `startLossyBank(lose, fault?)` for lost responses, HTML gateway errors, empty and truncated bodies, and `hang` + `release()` for a dispatch held in flight); never mock `bankRequest`. The `http/` handlers are covered by `app/api/[...path]/route.test.ts`. Run `npm run scenario` (failure scenarios) for end-to-end checks and `npm run typecheck`.

### Common Patterns

- The bank port (`../platform/bank/bank.ts`) is the only way to call the bank; always pass the server-known `ctx.userId`.
- Intent ids are `<runId>:<tool call_id>`, giving one intent per model tool call.
